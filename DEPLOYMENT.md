# Развёртывание NetAI Monitor на предприятии

Пошаговая инструкция по вводу в эксплуатацию с нуля: от чистого сервера до
работающей системы у всех инженеров NOC. Рассчитана на IT-специалиста,
разворачивающего систему, а не на конечного пользователя интерфейса.

Компонентов четыре, и они физически независимы друг от друга (подробнее
об архитектуре — в README.md, раздел «Сервис реального времени»):

| Компонент | Где живёт | Обязателен? |
|---|---|---|
| PostgreSQL + pgvector | сервер | нет — без него откат на локальный SQLite без RAG |
| Ollama | сервер (или тот же хост, что PostgreSQL) | нет — без неё анализ по ключевым словам, без ИИ |
| `realtime_service.py` | сервер, постоянно (служба Windows) | нет — без него нет автоматического опроса Zabbix |
| `NetAI Monitor` (десктоп) | ПК каждого инженера | да, это и есть само приложение |

### Кто с кем общается

```
Zabbix ──(только с сервера, напр. через L2TP-туннель)──┐
                                                       ▼
                        realtime_service.py  ──анализ──▶ Ollama (на сервере)
                                   │
                                   ▼ (пишет инциденты + свой статус)
                             PostgreSQL  ◀──(читают/пишут по LAN)── десктоп-клиенты
                                                                          │
                                                        (чат, аудит конфигов, RAG-сравнение)
                                                                          ▼
                                                              Ollama по LAN (порт 11434)
```

Ключевое следствие: **десктоп-клиенты к Zabbix не обращаются вообще.**
Опрос делает только служба на сервере, у которой есть туннель. Поэтому в
интерфейсе параметры Zabbix показаны только для чтения, а вместо кнопки
«Проверить подключение» там выводится состояние **от службы** (её heartbeat
в БД) — локальная проверка с десктопа всегда показывала бы «недоступно»
даже при полностью здоровой системе.

К Ollama, наоборот, обращаются и служба (для анализа инцидентов), и
десктопы (для чата, аудита конфигураций и сравнения «с RAG / без RAG») —
поэтому её нужно открыть в локальную сеть (см. шаг 2).

Ниже — порядок, в котором это разумно поднимать: сначала общая
инфраструктура на сервере, потом служба, потом клиенты у инженеров.

## Шаг 1. PostgreSQL + pgvector на сервере

1. Установите PostgreSQL 14+ (если ещё не установлен).
2. Установите расширение [pgvector](https://github.com/pgvector/pgvector) —
   на Windows проще всего взять готовую сборку под вашу версию PostgreSQL,
   на Linux — собрать из исходников (`make && make install`) или поставить
   пакет `postgresql-*-pgvector`, если он есть в вашем дистрибутиве.
3. Создайте базу данных и пользователя (или используйте существующего
   `postgres`):
   ```sql
   CREATE DATABASE netai_monitor;
   ```
   Таблицы, индексы и само расширение `vector` в этой базе приложение
   создаст автоматически при первом подключении (см. `db.py: SCHEMA`) —
   вручную создавать их не нужно, только саму базу.

### Разрешить подключения из локальной сети

По умолчанию PostgreSQL слушает только `localhost`. Чтобы десктоп-клиенты
с других машин могли подключаться:

1. В `postgresql.conf` (обычно рядом с `data/`, у Windows — в каталоге
   установки PostgreSQL):
   ```
   listen_addresses = '*'
   ```
2. В `pg_hba.conf` — добавить строку, ограниченную вашей подсетью (не
   открывайте на весь интернет):
   ```
   host    netai_monitor    all    192.168.1.0/24    scram-sha-256
   ```
3. Открыть порт в файрволе (PowerShell от администратора, Windows):
   ```powershell
   New-NetFirewallRule -DisplayName "PostgreSQL NetAI" -Direction Inbound `
     -Protocol TCP -LocalPort 5432 -RemoteAddress 192.168.1.0/24 -Action Allow
   ```
4. **Перезапустить службу PostgreSQL** (не `pg_reload_conf()` — некоторые
   параметры, включая `lc_messages` ниже, требуют полного рестарта).

### Локаль на Windows (важно)

Если PostgreSQL установлен с русской локалью, по умолчанию сервер отвечает
системными сообщениями в кодировке Windows-1251 — `psycopg2` пытается
декодировать их как UTF-8 и падает с `UnicodeDecodeError`, маскируя
реальную причину отказа подключения (неверный пароль, порт и т.п.). В
`postgresql.conf`:
```
lc_messages = 'C'
```
и снова перезапустить службу.

## Шаг 2. Ollama на сервере (с доступом из локальной сети)

```bash
ollama pull gemma3:4b          # или qwen2.5:3b — модель анализа, любая под ваши мощности
ollama pull nomic-embed-text   # модель эмбеддингов, нужна для RAG
```

К Ollama обращаются не только служба (локально), но и десктоп-клиенты
инженеров — для чата, аудита конфигураций и сравнения «с RAG / без RAG».
По умолчанию Ollama слушает только `localhost`, поэтому её нужно открыть
в локальную сеть:

1. Задать переменную окружения (машинную, чтобы подхватилась службой Ollama)
   и перезапустить Ollama:
   ```powershell
   [Environment]::SetEnvironmentVariable("OLLAMA_HOST", "0.0.0.0", "Machine")
   Restart-Service ollama    # либо перезапустить приложение Ollama вручную
   ```
2. Открыть порт `11434` только для своей подсети:
   ```powershell
   New-NetFirewallRule -DisplayName "Ollama NetAI" -Direction Inbound `
     -Protocol TCP -LocalPort 11434 -RemoteAddress 192.168.1.0/24 -Action Allow
   ```

Проверка с десктопа: вкладка **Настройки → Проверка подключений с этого
компьютера** → «Проверить» у Ollama должно дать «модель доступна».

## Шаг 4. Настроить подключения

Настройки разделены по месту применения — это важно понимать, иначе легко
искать их не там:

| Что | Где задаётся | Кто использует |
|---|---|---|
| Подключение к Zabbix (URL/логин/пароль), интервал опроса, DSN к БД для службы | `%PROGRAMDATA%\NetAI Monitor\service_config.json` **на сервере** (см. шаг 5) | только служба |
| Подключение к PostgreSQL для десктопа | Настройки → PostgreSQL (или `NETAI_DB_DSN`), локально на каждом ПК | десктоп-клиент |
| Ollama host / модель / модель эмбеддингов | Настройки в приложении (хранится в общей БД) | десктоп-клиенты |
| Тема оформления | локально, `%APPDATA%\NetAI Monitor\ui_theme.json` | десктоп-клиент |

**Десктоп-клиент**: запустите `python main.py`, вкладка **Настройки**:
- **PostgreSQL** — хост/порт/база/логин/пароль, кнопка «Проверить
  подключение», сохранение переключает приложение с локального SQLite на
  PostgreSQL (нужен перезапуск). Либо переменной окружения:
  ```bash
  setx NETAI_DB_DSN "dbname=netai_monitor user=postgres password=... host=<IP сервера> port=5432"
  ```
- **Ollama для этого приложения** — адрес сервера, где запущена Ollama
  (например `http://192.168.1.10:11434`), и названия моделей.
- **Источники данных (настраиваются на сервере)** — параметры Zabbix
  показаны только для чтения: их задаёт служба в своём
  `service_config.json`, а здесь видно, с чем она работает.
- Чекбокс «Использовать синтетические данные» на вкладке «Синтетические
  данные» влияет на **это приложение** (Генератор, демо-режим). Демо-режим
  самой службы включается отдельно — полем `use_synthetic_data` в её
  конфиге, чтобы никто с произвольного ПК не перевёл серверный опрос в
  синтетику случайно.

## Шаг 5. Настроить и запустить службу реального времени

Именно она опрашивает Zabbix и вызывает LLM — работает постоянно на сервере,
независимо от того, открыт ли у кого-то десктоп-клиент.

### 5.1. Настройки службы

Служба берёт параметры НЕ из интерфейса приложения, а из собственного файла
на сервере:

```
%PROGRAMDATA%\NetAI Monitor\service_config.json
```

Почему отдельно от общих настроек в БД:
- доступ к Zabbix есть только у серверной машины (туннель поднят на ней) —
  задавать эти параметры с произвольного десктопа бессмысленно, поэтому в
  интерфейсе они показаны **только для чтения**;
- `ollama_host` у службы и у клиентов разный: для службы это `localhost`
  сервера, для десктопов — IP того же сервера;
- служба Windows работает под системной учётной записью и **не видит**
  `%APPDATA%` вашего пользователя, где лежит `postgres_connection.json` —
  поэтому у неё свой DSN в этом файле (`%PROGRAMDATA%` виден всем).

Файл создаётся автоматически при первом запуске службы (или скриптом
установки ниже). Заполните:

```json
{
  "postgres_dsn": "dbname=netai_monitor user=postgres password=... host=localhost port=5432",
  "zabbix_url": "http://10.10.11.25/zabbix",
  "zabbix_user": "Admin",
  "zabbix_password": "...",
  "ollama_host": "http://localhost:11434",
  "ollama_model": "gemma3:4b",
  "embedding_model": "nomic-embed-text",
  "use_synthetic_data": false,
  "poll_interval_seconds": 60
}
```

Изменения применяются после перезапуска службы.

### 5.2. Установка службой Windows (NSSM)

1. Скачайте [NSSM](https://nssm.cc/download) и положите `nssm.exe` в
   `tools\nssm.exe` (или добавьте в `PATH`).
2. В PowerShell **от администратора**, из корня проекта:

```powershell
.\tools\install_service.ps1
```

Скрипт создаёт службу `NetAIMonitorRealtime` с автозапуском при загрузке
компьютера и автоперезапуском при падении процесса. Управление —
`services.msc` или `nssm start/stop/restart NetAIMonitorRealtime`.
Удаление — `.\tools\install_service.ps1 -Remove`.

Запуск вручную (для проверки/отладки) по-прежнему работает:

```bash
python realtime_service.py
```

Вторая копия не запустится: служба держит файловую блокировку, иначе два
процесса дублировали бы опрос и вызовы LLM.

### 5.3. Как понять, что служба работает

- **Из интерфейса приложения (с любого ПК)** — вкладка **Настройки**,
  карточка «Сервис реального времени»: состояние, когда был последний
  опрос, доступен ли Zabbix **серверу**, сводка последнего цикла и имя
  сервера. Если отметки нет больше 3 минут — показывается предупреждение
  (долгий LLM-анализ при этом за сбой не считается, у него свой статус).
- **Лог службы** (с ротацией, 5 файлов по 5 МБ):
  ```
  %PROGRAMDATA%\NetAI Monitor\logs\realtime.log
  ```
  Ожидаемые строки: `Опрашиваю Zabbix...`, `Zabbix вернул N активных
  проблем.`, затем `новых: N, закрыто: M, повторно проанализировано: K`
  (или «изменений нет»).

Если PostgreSQL в момент старта ещё не поднялся (типично при перезагрузке
сервера — службы стартуют в произвольном порядке), служба не падает: пишет
в лог «PostgreSQL недоступен… Повтор через 15 сек» и поднимается сама.
На локальный SQLite она при этом сознательно **не** переключается — иначе
результаты анализа ушли бы в файл, которого не видит ни один клиент.

## Шаг 6. Раздать десктоп-клиент инженерам

Два варианта.

**А. Установщик (рекомендуется для инженеров без Python)** — собирается
один раз на любой Windows-машине с установленным проектом:
```bash
pip install pyinstaller
pyinstaller netai_monitor.spec --clean
# результат: dist/NetAI-Monitor/NetAI-Monitor.exe

# затем (нужен Inno Setup — https://jrsoftware.org/isinfo.php):
"C:\Program Files (x86)\Inno Setup 6\ISCC.exe" installer.iss
# результат: installer_output/NetAI-Monitor-Setup.exe
```
Раздайте `NetAI-Monitor-Setup.exe` инженерам — ставится без прав
администратора, в пользовательский профиль. После первого запуска каждый
инженер один раз указывает в **Настройках** параметры подключения к общей
PostgreSQL (шаг 4) — дальше всё остальное подтягивается из БД само.

**Б. Из исходников** — на машине с Python:
```bash
git clone https://github.com/agpmen-psk/NetAI-monitor.git
cd NetAI-monitor
pip install -r requirements.txt
python main.py
```

## Шаг 7. Проверка работоспособности

1. Откройте десктоп-клиент → вкладка **Настройки** → «Проверить
   подключение» для PostgreSQL и «Проверить» для Zabbix/Oxidized/Ollama —
   все четыре должны отвечать «✓ подключение успешно» / «✓ модель доступна».
2. Убедитесь, что `realtime_service.py` пишет в лог реальные циклы опроса
   (шаг 5).
3. Дождитесь (или дождитесь следующей минуты) — новый алерт должен
   появиться во вкладке **Алерты** и всплыть тостом в правом нижнем углу.
4. Вкладка **Дашборд** должна показывать ненулевые метрики после того, как
   накопится история.

Если что-то не работает — приложение не падает, а честно деградирует
(см. таблицу в начале файла): отключённый компонент просто перестаёт
давать свою часть функциональности, остальное продолжает работать.

## Частые проблемы

| Симптом | Причина | Решение |
|---|---|---|
| `UnicodeDecodeError` при подключении к PostgreSQL | `lc_messages` в русской локали | См. «Локаль на Windows» в шаге 1 |
| PostgreSQL недоступен со второй машины, хотя на сервере всё работает | не открыт порт/не разрешён хост | Проверить `pg_hba.conf`, `listen_addresses`, файрвол (шаг 1) |
| Приложение стартует, но БД молча переключилась на SQLite | Неверный DSN/пароль, PostgreSQL не запущен | Проверить `NETAI_DB_DSN` / вкладку Настройки → PostgreSQL → «Проверить подключение» |
| Инциденты не анализируются вовсе | Служба не запущена или упала | Настройки → «Сервис реального времени» покажет состояние; лог `%PROGRAMDATA%\NetAI Monitor\logs\realtime.log`. Кнопка «Обновить список» в GUI тут не поможет — это только чтение из БД |
| `RAG недоступен` в интерфейсе | Нет модели `nomic-embed-text` в Ollama, либо PostgreSQL в офлайн-режиме (SQLite) | `ollama pull nomic-embed-text`; RAG вообще недоступен без PostgreSQL (нужен pgvector) |
| В GUI «Сервис реального времени: не отвечает», хотя служба запущена | Служба не может писать в ту же БД, что читает клиент (разные DSN), либо процесс висит | Сверить `postgres_dsn` в `service_config.json` с тем, к чему подключён клиент; посмотреть лог службы |
| В GUI «служба ни разу не запускалась» | Клиент и служба смотрят в РАЗНЫЕ базы (например, клиент откатился на локальный SQLite) | Статусная строка внизу окна покажет «БД: SQLite офлайн» — значит клиент не видит серверную БД, проверьте подключение к PostgreSQL |
| Служба в логе пишет «Служба уже запущена» и выходит | Уже работает копия (служба Windows + ручной запуск) | Это защита от дублирования анализа. Остановите лишнюю копию: `nssm stop NetAIMonitorRealtime` либо закройте консоль |
| Чат/аудит конфигов не работают с десктопа, а на сервере работают | Ollama слушает только localhost | Открыть Ollama в локальную сеть — `OLLAMA_HOST=0.0.0.0` + правило файрвола (шаг 2) |
