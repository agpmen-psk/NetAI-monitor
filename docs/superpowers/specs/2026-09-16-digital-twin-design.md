# Цифровой двойник сети (Digital Twin) — дизайн

Дата: 2026-09-16
Статус: одобрено пользователем в чате, ожидает финального ревью спеки перед переходом к плану реализации.

## Проблема и мотивация

Приложение сейчас анализирует инциденты либо из настоящего Zabbix, либо из
`MockZabbixClient` — генератора без какой-либо связи с реальной топологией
сети предприятия (случайный хост из плоского списка + случайный шаблон
проблемы). Для того чтобы:

1. накопить содержательный, органически растущий датасет для RAG (а в
   перспективе — для дообучения модели), где пользователь как инженер
   лично проверяет алерты и пишет настоящие решения;
2. дать LLM реалистичный контекст конкретно ЭТОЙ сети (не абстрактных
   `SW-CORE-01`, а настоящих `PSE-PSK-MAR-h2600-BR-1` с реальными ролями и
   связями);
3. не подключаться к боевому Zabbix предприятия ради экспериментов,

нужен генератор событий, который ведёт себя как настоящий мониторинг:
знает топологию сети, роняет и поднимает узлы правдоподобно, и умеет
каскадные сбои (если падает граница — недоступны все площадки за ней).

## Решение в одном абзаце

Новый модуль `digital_twin.py` с классами `TwinZabbixClient` /
`TwinOxidizedClient`, реализующими **тот же интерфейс**, что уже есть у
`MockZabbixClient`/`MockOxidizedClient` (`get_active_problems()`,
`get_nodes()`, `get_diff()` и т.д.) — подключаются вместо них через новый
режим `synthetic_data_mode: "twin"` в `service_config.json`, без изменений
в `realtime_service.py`/`job_worker.py`/`api_server.py` кроме выбора
класса. Внутреннее состояние («что сейчас сломано») живёт в новой таблице
`twin_incidents` в PostgreSQL — переживает перезапуск служб. Топология —
реальная сеть предприятия, зафиксирована в `twin_data/network_topology.json`
(вне git, см. `.gitignore`) на основе присланного пользователем реестра
оборудования (50 узлов, 23 площадки).

## Архитектура

```
service_config.json: synthetic_data_mode = "off" | "flat" | "twin"
                                │
                    ┌───────────┼───────────┐
                    │           │           │
                 "off"       "flat"       "twin"
                    │           │           │
              ZabbixClient  MockZabbix   TwinZabbixClient ──┐
              OxidizedClient MockOxidized TwinOxidizedClient │
                                                              │
                                                    читает/пишет
                                                              ▼
                                                    twin_incidents (PostgreSQL)
                                                              │
                                            (на старте, один раз) читает
                                                              ▼
                                              twin_data/network_topology.json
```

`realtime_service.py._build_clients()` и `job_worker.py._build_oxidized_client()`
получают третью ветку выбора клиента. Дальше — **ничего не меняется**:
`TwinZabbixClient.get_active_problems()` возвращает `List[Incident]`, эти
инциденты идут в `analyzer.analyze()` → сохраняются в `incidents` → вы
проверяете как инженер → RAG учится. Вся эта часть пайплайна уже
существует и не трогается.

## Топология

### Формат `network_topology.json`

```json
{
  "sites": {"psk-hq": "г. Псков, ул. К. Маркса, д. 1А", ...},
  "redundancy_groups": {},
  "nodes": [
    {
      "name": "PSE-PSK-MAR-h2600-BR-1",
      "role": "border_router",
      "vendor": "H3C", "model": "MSR2600-6-X1 Router",
      "site": "psk-hq", "ip": "10.199.223.68",
      "criticality": "HIGH",
      "depends_on": [],
      "purpose": ""
    },
    ...
  ]
}
```

`depends_on` — список имён узлов ИЛИ ключей `redundancy_groups` (группа
резервирования жива, пока жив хотя бы один член — каскад к зависимым от
группы срабатывает, только когда упали ВСЕ члены). Сейчас
`redundancy_groups` пуст: ядро Пскова — IRF-стек (для мониторинга это один
логический узел с одним IP, резервирование уже отражено самим фактом
единственной ноды), граница — не резервирована по факту.

### Текущее состояние (сгенерировано `twin_data/build_topology.py`)

50 узлов, 23 площадки: главная (Псков, К.Маркса 1А — граница → ядро IRF →
5×Eltex access + 6×HPE access для принтеров/очереди/CCTV/биллинга +
Mikrotik очереди, все зависимые от `ASW-1`), филиал М.Горького и Великие
Луки (свой погран-роутер, зависит от главной границы), плюс 20 районных
площадок (H3C-роутер, часть с Eltex access-свитчем) — все зависят от
главной границы. Серверы/ВМ из диаграммы (StateWatcher, SIEM и т.п.) —
намеренно не включены (по решению пользователя, «сервера не надо пока»).

## Модель поведения (`TwinZabbixClient`)

На каждый вызов `get_active_problems()`:

1. **Разрешение существующих проблем.** Для каждой незакрытой root-cause
   записи в `twin_incidents`, у которой `resolve_at <= now()`, — помечаем
   решённой. Если это открывало каскад (у зависимых узлов не было других
   путей), закрываем и каскадные записи, у которых `caused_by` указывает
   на неё.
2. **Появление новых root-cause событий.** Вероятность на тик зависит от
   `twin_incident_rate_per_day` (новый параметр `service_config.json`,
   дефолт **50/сутки** — при `poll_interval_seconds=60` это вероятность
   нового root-cause события ≈3.5% на каждый тик опроса; легко уменьшить
   позже, когда датасета накопится достаточно). Узел выбирается взвешенно: `HIGH`
   криticality — реже, но диспропорционально тяжелее по последствиям
   (каскад больше); `LOW` — чаще, локальнее. Тип проблемы — из
   расширенного пула шаблонов (переиспользуем/дополняем
   `MockZabbixClient.PROBLEM_TEMPLATES`, с уклоном под реальные роли:
   `border_router`/`core_switch` — BGP/OSPF/link down/power, `access_switch`
   — port flap/errors, `edge_router` — agent unavailable/high latency).
3. **Каскад.** BFS/обход `depends_on` от узла с новым root-cause: для
   каждого зависимого узла без альтернативного живого пути — создаём
   вторичную запись `twin_incidents` с `caused_by = <root_host>` и
   характерным для роли текстом («Lost connection to <host> (ICMP)»), но
   **с явной пометкой причины прямо в `problem_name`**:
   `"Lost connection to PSE-PSK-KRG-h2600-BR-1 (ICMP) [вероятно каскад от
   отказа PSE-PSK-MAR-h2600-BR-1]"`. Это сознательно простое решение —
   не трогаем `Incident`/схему БД/`llm_client.py`, модель получает
   причинно-следственную связь прямо текстом, а существующая логика
   корреляции в `_correlate_incidents` (по хосту+времени) продолжает
   работать как есть для проблем на одном узле.
4. Возвращаем `List[Incident]`, собранные из всех незакрытых
   `twin_incidents` — так же, как раньше `MockZabbixClient` отдавал
   `self._active.values()`.

### Таблица `twin_incidents`

```sql
CREATE TABLE IF NOT EXISTS twin_incidents (
    id              TEXT PRIMARY KEY,
    host            TEXT NOT NULL,
    problem_name    TEXT NOT NULL,
    severity        INT NOT NULL,
    item_key        TEXT,
    last_value      TEXT,
    started_at      TIMESTAMP NOT NULL DEFAULT now(),
    resolve_at      TIMESTAMP,
    is_root_cause   BOOLEAN NOT NULL DEFAULT true,
    caused_by       TEXT,
    resolved        BOOLEAN NOT NULL DEFAULT false,
    resolved_at     TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_twin_incidents_open ON twin_incidents (resolved) WHERE resolved = false;
```

Отдельная от `incidents` (та хранит уже проанализированные LLM и
проверенные инженером записи) — `twin_incidents` это внутренняя «память
мира» симуляции, не видна напрямую в GUI.

## `TwinOxidizedClient` (упрощённо в MVP)

Периодически (независимо от Zabbix-части) генерирует diff/полный конфиг
для случайного узла топологии, используя реалистичные для его вендора
(H3C/Eltex) паттерны рисков — переиспользуем стиль
`mock_oxidized_client.py: SYNTHETIC_DIFFS`, но с реальными именами узлов.
**Связь «конфиг вызвал инцидент» — намеренно НЕ в MVP**, отдельная фаза 2
(решено с пользователем).

## Конфигурация

`service_config.json`, новые/изменённые поля:
```json
{
  "synthetic_data_mode": "twin",
  "twin_topology_file": "network_topology.json",
  "twin_incident_rate_per_day": 50
}
```
Обратная совместимость: если `synthetic_data_mode` отсутствует — читаем
старый `use_synthetic_data` (`true` → `"flat"`, `false` → `"off"`), чтобы
не сломать уже развёрнутые окружения без ручной правки конфига.

`twin_topology_file` — путь ищем сначала рядом с `service_config.json`
(`%PROGRAMDATA%\NetAI Monitor\`), администратор кладёт туда файл вручную
при разворачивании (сгенерированный `twin_data/build_topology.py` или
отредактированный вручную).

## Ошибки и границы

- Топология не найдена/битый JSON при `synthetic_data_mode = "twin"` —
  служба логирует понятную ошибку и не падает (как сейчас с отсутствующим
  `service_config.json` — `ensure_config_file()`), но не работает, пока
  файл не появится (аналогично отсутствию доступа к боевому Zabbix).
- `depends_on` ссылается на несуществующий узел — обнаруживается при
  загрузке (валидация, как в `twin_data/build_topology.py`), логируется
  предупреждение, узел считается без зависимостей (не блокирует запуск
  сервиса из-за одной опечатки).
- Гонка при каскаде (родитель уже "починился" ровно в момент решения о
  каскаде) — приемлемо на уровне симуляции, не требует транзакционной
  строгости (это не боевые данные, а обучающий материал).

## Тестирование

- Юнит-тест загрузки/валидации топологии: битые `depends_on`, дубликаты
  имён узлов, отсутствующий файл.
- Функциональный тест `TwinZabbixClient` с фиксированным seed: несколько
  тиков подряд — проверка, что (а) каскад реально создаёт вторичные записи
  для зависимых узлов, (б) при появлении второго живого пути (когда
  появятся redundancy_groups) каскад подавляется, (в) решение root-cause
  закрывает и его каскадные записи, (г) состояние переживает создание
  НОВОГО экземпляра `TwinZabbixClient`, указывающего на ту же БД (эмуляция
  перезапуска службы).

## Явно вне рамок MVP (следующие этапы)

1. Связь Oxidized-diff → root-cause инцидента в Zabbix-части.
2. `redundancy_groups` для реальных резервированных пар — добавится, когда
   будут подтверждены hostname/IP вторых юнитов (сейчас в реестре
   оборудования такие записи не найдены).
3. Серверы/ВМ как отдельные узлы топологии.
4. Ручной триггер конкретного сценария из GUI (сейчас только автономная
   генерация).
5. Дообучение модели (fine-tuning) — отдельная большая тема, обсуждалась
   отдельно; данный двойник — способ нарастить для неё датасет.
